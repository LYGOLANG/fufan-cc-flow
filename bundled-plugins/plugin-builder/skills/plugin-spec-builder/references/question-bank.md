    想瞎问时看 [主问题]，想接受敷衍时看 [不接受的答案]，想提前停时看 [接受标准]。

[纪律 · 用户面前不暴露内部标签]
    Phase、维度编号、P0、Gate、评分和题库名称只用于内部追踪。

    - “Phase 2 已锁定。”

    - 技术实现由 Architect 决定，不要求用户回答他不懂的专业问题。

[Phase 1 · Plugin 基本盘]

    [1.1 · 核心结果]
        [覆盖意图]
            “做个画布”“做个视频工具”只是形态，不是结果。核心结果决定所有功能取舍和验收。

        [主问题]
            - 用户完成一次核心任务后，手里具体多了什么、少了什么，或什么状态发生了变化？
            - 如果首版只能证明一件事，它必须证明什么？

        [追问深化]
            - 用户说“提高效率” → “现在一遍要多久、哪一步最慢？Plugin 做完后你希望变成什么具体流程？”
            - 用户说“更智能” → “智能在哪个决定上？它要读取什么，替用户做什么，结果怎么判断对不对？”
            - 用户说“方便编辑” → “编辑什么对象，完成后得到哪个文件或项目状态？”
            - 用户说“像 Cowart” → “你真正要复用的是无限画布、UI 触发 Agent、结果回写，还是安装形态？挑核心。”

        [接受标准]
            - 一句话能描述可观察结果，不依赖抽象形容词。
            - 能给出一个真实输入和真实输出例子。

        [不接受的答案]
            - “提升体验 / 提高效率 / 更智能 / 更专业”
            - “什么都能做”
            - 只说技术栈或界面形态

    [1.2 · 主用户与场景]
        [覆盖意图]
            同一个 Plugin 给创作者、开发者和运营人员，入口、术语、默认和权限完全不同。

        [主问题]
            - 画一个最典型的人：他是什么角色，在什么项目里，什么时刻打开这个 Plugin？
            - 他打开前已经有什么材料，脑中在想什么？

        [追问深化]
            - 用户说“所有人” → “先挑首版会每天用它的那类人。其他人能用不等于为他们设计。”
            - 用户说“内容创作者” → “做视频、图片、播客还是社媒？独立创作者和团队编辑的流程也不一样。”
            - 用户说“开发者” → “是在写代码时用，还是在做可视化内容时用？宿主上下文不同。”

        [接受标准]
            - 有一个主角色、一个触发场景、一个已有项目或材料状态。
            - 能说明为什么他会在 Claude Code / Codex 里而不是另开独立 App。

        [不接受的答案]
            - “所有用户 / 有需要的人 / 创作者”
            - 没有具体发生时刻

    [1.3 · 当前替代与痛点]
        [覆盖意图]
            不知道现有流程，就无法判断 Plugin 应消灭哪一步、保留哪一步，也无法避免做一个更麻烦的新工具。

        [主问题]
            - 现在用户怎么完成这件事？按顺序说一遍。
            - 最浪费时间、最容易错或最需要来回沟通的是哪一步？

        [追问深化]
            - 用户说“现在很麻烦” → “麻烦发生在哪个动作？要复制文件、切应用、重复描述，还是等结果后手工放回？”
            - 用户说“没有替代方案” → “那用户现在是放弃不做，还是用聊天、脚本、Figma、Premiere、表格拼出来？”

        [接受标准]
            - 能列出现有流程的主要步骤。
            - 指出至少一个可被 Plugin 明确改写的瓶颈。

        [不接受的答案]
            - “不方便 / 很麻烦 / 体验不好”但说不出具体步骤

    [1.4 · 为什么需要 Plugin 与 GUI]
        [覆盖意图]
            不是所有问题都需要 iframe、Browser 或富 UI。GUI 必须承担聊天做不好的直接操作、持续状态或可视反馈。

        [主问题]
            - 哪些事情用户必须亲手拖、选、画、调、比较或预览，纯聊天会明显变差？
            - 为什么不能只做一个 Skill 或命令？

        [追问深化]
            - 用户说“有个面板更直观” → “面板里有什么必须直接操作的对象？如果只是填 3 个字段，可能不值得做复杂 Plugin。”
            - 用户说“看起来高级” → “UI 不是装饰。它要减少哪种歧义或给用户哪种精确控制？”
            - 用户没有直接操作 → “那首版更可能是 Skill + MCP Tool。你是否仍有必须可视化的状态或结果？”

        [接受标准]
            - 至少一个 GUI 独有价值：空间选择、时间选择、直接操作、持续预览、复杂状态、并排比较等。
            - 若无 GUI 必要性，明确改为其他 Plugin 类型，不强行交互式。

        [不接受的答案]
            - “更好看 / 更直观 / 像 App”
            - 只有聊天输入框复制到网页

    [1.5 · 目标宿主优先级]
        [覆盖意图]
            Claude Code、Claude Web/Desktop、ChatGPT/Codex 和 CLI 的 UI、消息与安装能力不同。首版必须有基准目标。

        [主问题]
            - 首版必须在哪个环境真实可用？Claude Code、ChatGPT/Codex，还是两者？
            - 如果两者体验不同，哪一个是 required 基准，哪一个可以后补或降级？

        [追问深化]
            - 用户说“都一样支持” → “宿主能力不会完全一样。先定 required，另一个设 optional；否则验收会失真。”
            - 用户只说“Claude” → “是 Claude Code、Claude Desktop 还是网页 Claude？它们不是同一个运行面。”
            - 用户只说“Codex” → “是要嵌进 ChatGPT 聊天（那是嵌入面），还是在 Codex CLI / IDE / 桌面里用（那里工具可用但界面走浏览器）？首版 UI 要落在哪个面？”

        [接受标准]
            - 至少一个 required target。
            - 每个 target 有 tier 和可接受的用户体验边界。

        [不接受的答案]
            - “Claude / Codex 都行”但无主次
            - 把产品名当成精确宿主环境

[Phase 2 · Golden Path 与直接操作]

    [2.1 · 打开与第一屏]
        [覆盖意图]
            Plugin 能安装不等于用户知道如何开始。打开入口和初始状态决定首个成功率。

        [主问题]
            - 用户安装后，用一句什么话、一个什么命令或哪个入口打开？
            - 第一次打开是空工作区、加载当前项目，还是要求选择 / 导入内容？

        [追问深化]
            - 用户说“打开就能用” → “打开后具体看到哪个对象和下一步动作？空白画布往往让人不知道做什么。”
            - 用户说“自动读取项目” → “读哪些文件，找不到时怎么提示，是否要用户确认？”

        [接受标准]
            - 打开入口、初始数据来源、空状态 CTA 明确。

        [不接受的答案]
            - “跟普通软件一样”
            - 没有空状态或首个动作

    [2.2 · 输入与来源]
        [覆盖意图]
            输入来源决定文件权限、预览、解析、缓存和错误处理。

        [主问题]
            - 核心任务的真实输入是什么？来自当前项目、用户选择文件、粘贴、拖入，还是 Agent 生成？
            - 给一个首版样本：格式、数量和大致大小。

        [追问深化]
            - 用户说“支持图片 / 视频” → “首版最常见的 2-3 种格式和最大样本是什么？RAW、4K、多轨都会改变实现。”
            - 用户说“从项目自动识别” → “识别规则是什么，多个候选时谁选？”

        [接受标准]
            - 每种 must 输入有来源、格式、数量 / 规模、找不到时行为。

        [不接受的答案]
            - “常见格式都支持”
            - “随便拖进来”但无保存位置和失败边界

    [2.3 · UI 直接操作]
        [覆盖意图]
            高频精确操作应该留在 UI，不经过模型。必须定义对象、动作和即时反馈。

        [主问题]
            - 用户在 UI 中最常做的三个动作是什么？逐个说对象、手势和结果。
            - 哪些动作必须立即响应，不能等 Agent？

        [追问深化]
            - 用户说“编辑” → “选中什么、改哪个属性、拖到哪里、完成后画面如何变化？”
            - 用户说“时间线操作” → “首版是裁切、分割、移动、缩放、轨道还是字幕？不能把专业剪辑器全吞进去。”
            - 用户说“画布” → “首版需要多选、图层、对齐、缩放、标注中的哪些？核心任务依赖哪几个？”

        [接受标准]
            - 至少一个核心对象模型和 3 个高频动作。
            - 每个动作的本地反馈、保存时机和是否触发 Agent 明确。

        [不接受的答案]
            - “支持拖拉拽”但不知道拖什么、放哪、结果是什么
            - “像 Figma / Premiere 一样”

    [2.4 · Agent 触发点]
        [覆盖意图]
            如果触发点模糊，UI 和聊天会互相抢控制权，Agent 也拿不到准确上下文。

        [主问题]
            - 用户在哪个明确动作后希望 Agent 接手？点击按钮、从聊天发话，还是两种都要？
            - 触发时 UI 应自动附带哪些当前选择或范围？

        [追问深化]
            - 用户说“随时和 Agent 聊” → “聊天里说‘这个’时，系统怎么知道指哪个对象或时间段？”
            - 用户说“自动触发” → “每次修改都触发会慢且贵。哪一个提交动作代表用户意图已经完整？”

        [接受标准]
            - 至少一个明确触发动作。
            - 当前对象、选择、范围、prompt 和资源引用的最低上下文明确。

        [不接受的答案]
            - “AI 自动理解当前页面”
            - 每个 pointer event 都交给 Agent

    [2.5 · 结果写回]
        [覆盖意图]
            Agent 产生结果后必须通过领域动作回到权威状态，而不是只在聊天中说“完成了”。

        [主问题]
            - Agent 完成后，界面具体发生什么：新增、替换、并排、应用 patch、创建版本还是只给建议？
            - 原内容要保留吗，是否需要用户确认？

        [追问深化]
            - 用户说“直接改” → “如果结果不好，怎么回退？哪些操作允许自动应用，哪些必须预览？”
            - 用户说“显示结果就行” → “结果显示在哪里，和哪个原对象关联，重开后还在吗？”

        [接受标准]
            - 结果类型、目标对象、位置、原内容策略、确认策略和持久化明确。

        [不接受的答案]
            - “AI 改完自动更新”但无目标和版本规则
            - 只在聊天中返回文字

    [2.6 · 保存、导出与下一步]
        [覆盖意图]
            核心结果必须能留在项目、导出或继续迭代，否则流程没有终点。

        [主问题]
            - 用户满意后，结果放在哪里，怎样继续使用？
            - 是自动保存项目状态、导出文件、下载，还是交给下一步工具？

        [追问深化]
            - 用户说“保存就行” → “保存工程状态还是最终产物？文件名、位置和覆盖规则由谁决定？”
            - 用户说“导出视频 / 图片” → “首版输出格式、分辨率和等待状态是什么？”

        [接受标准]
            - 项目状态与最终产物分别定义。
            - 用户下一步可执行。

        [不接受的答案]
            - “能下载”但没有格式、位置和失败行为

    [2.7 · 形态判定]
        [覆盖意图]
            开发形态在采访就要定下来，Design、Plan、Builder 全按它分支。判定前用户必须已知情两种形态各适合什么——不知情的选择会让后续需求沟通失效；已明白或自己点名形态的用户不重复教学。

        [主问题]
            - 先告知再问。参考基调（按用户业务现场举例改写，不逐字照念）：“插件的界面有两种做法，不管选哪种，你都能在对话里指挥 Agent 干活。一种是对话内嵌小面板——工具返回一个界面，支持的宿主直接嵌进聊天里，适合快速生成、调几个参数、选模板、增删条目、审阅确认、触发渲染导出、看预览这类点两下就完的轻交互；另一种是独立完整界面——Skill 让 Agent 启动一个 Web 应用，在浏览器里打开，适合无限画布、多轨时间线、拖拽框选、键盘快捷键、大量素材、大文件、密集渲染、长任务、复杂撤销这类完整编辑体验。”
            - “你想象用户用它时，是聊天里弹出个小面板点两下，还是打开一个完整界面拖来拖去？”

        [追问深化]
            - 用户说“要嵌在对话里” → “目标宿主是哪一个？嵌入渲染只在支持 MCP Apps 的对话宿主成立（ChatGPT、claude.ai / Claude Desktop 聊天端）；Claude Code 和 Codex（不管命令行、IDE 还是桌面）里工具照常对话可用，但界面不会嵌进对话。”
            - 用户说“两种都想要” → “可以做混合：同一套工具，对话里给轻控制和预览，完整编辑器一键打开。首版先以哪一层为基准？”
            - 用户说“无所谓 / 你定” → 按交互复杂度归纳：有拖拽、画布、时间线、大文件任一项 → companion-web-app；只有生成、调参、审阅 → 结合宿主给默认并说明理由，让用户行使否决权。

        [接受标准]
            - 形态结论（companion-web-app / mcp-app / hybrid）已确认，判定依据可追溯到界面位置、目标宿主、交互复杂度三项。
            - 用户能用自己的话说出选择理由；已懂的用户没有被重复教学。
            - mcp-app / hybrid 时用户已知情 tool-only 硬约束：全部工具在无嵌入 UI 的宿主仍可对话直用。

        [不接受的答案]
            - 用术语反问用户“要 MCP App 吗”而未先解释两种形态适合什么
            - 形态与 required target 的宿主能力矛盾却照单全收

[Phase 3 · Agent 协作与潜在能力]

    [3.1 · Agent 职责]
        [覆盖意图]
            Agent 应处理需要理解、规划、生成、跨工具和文件执行的任务；确定性直接操作不该交给模型。

        [主问题]
            - 哪些步骤必须由 Claude Code / Codex 判断或执行，普通前端逻辑做不好？
            - Agent 要调用哪些现成能力：代码、文件、命令、图片生成、浏览器、外部工具？

        [追问深化]
            - 用户说“所有智能功能” → “挑首版唯一最重要的语义任务。其他是同类变体还是独立能力？”
            - 用户说“让 Agent 修改界面” → “修改的是项目数据还是 DOM？应当通过领域 Tool 改权威状态。”

        [接受标准]
            - Agent 任务有清晰输入、判断、执行和结果。
            - 与本地 UI 职责不重叠。

        [不接受的答案]
            - “AI 帮忙 / AI 自动处理”
            - 用 Agent 替代简单排序、拖拽、校验

    [3.2 · 交给 Agent 的上下文]
        [覆盖意图]
            自然语言中的“这个”“刚才那段”必须落到结构化引用，且大文件不能盲目塞入上下文。

        [主问题]
            - Agent 要准确执行，最低需要知道哪些对象 ID、选择范围、文件路径、截图或项目版本？
            - 哪些内容只传引用，哪些需要附带预览？

        [追问深化]
            - 用户说“把画布给 Agent 看” → “是整个画布截图，还是当前选区、关联对象和标注？全量通常噪声更大。”
            - 用户说“把视频发给 Agent” → “模型不应吃完整视频字节。需要转录、抽帧、时间范围和文件引用中的哪些？”

        [接受标准]
            - 有最小上下文 envelope，能消除指代歧义。
            - 大文件采用引用或派生摘要。

        [不接受的答案]
            - “Agent 会看到当前状态”但未定义状态
            - 把整个项目 / 大文件 Base64 传给模型

    [3.3 · 结果应用策略]
        [覆盖意图]
            自动替换、并排比较和提案模式对控制权、历史和 Tool 设计影响不同。

        [主问题]
            - 结果默认是自动应用、先预览，还是创建一个新版本放旁边？
            - 哪些情况允许覆盖，哪些必须保留原内容？

        [追问深化]
            - 用户说“看情况” → “按破坏性分级：可逆小改自动应用，生成和删除先预览，这个默认是否合适？”
            - 用户同时要覆盖和保留 → “保留版本后再把当前指针切到新结果，还是完全不改原对象？”

        [接受标准]
            - 默认策略和破坏性例外明确。

        [不接受的答案]
            - “AI 自己判断要不要覆盖”

    [3.4 · 生成与修改控制]
        [覆盖意图]
            AI 任务会失败、重复、超时和产生多版本。最低控制能力要在首版边界中明确。

        [主问题]
            - 用户等待时至少要看到什么？状态、阶段、百分比还是结果占位？
            - 需要取消、重试、多个版本或保留原始结果中的哪些？

        [追问深化]
            - 用户说“转圈就行” → “如果任务两分钟、关闭后重开或失败，转圈不足以恢复。你的最长真实任务大概多久？”
            - 用户说“无限重试” → “重试会不会重复收费、重复文件或重复插入？需要 requestId 和幂等。”

        [接受标准]
            - 对实际最长任务有可接受反馈和恢复规则。
            - 重复提交和失败结果不破坏原状态。

        [不接受的答案]
            - “失败就再点一次”但会产生重复副作用

    [3.5 · 连带需求]
        [覆盖意图]
            用户常只说主动作，忽略使其可用的选择、撤销、版本、进度、权限和历史。

        [主问题]
            - 不直接问全清单。根据当前场景提出最多 1-2 个必需连带能力，并解释不做会在哪里断。

        [追问深化]
            - 上传 → 类型 / 大小 / 多文件 / 进度 / 保存位置 / 失败。
            - 画布 → 视口 / 多选 / 图层 / 自动保存 / 撤销。
            - 时间线 → 缩放 / 播放头 / 裁切 / 轨道 / 预览 / 导出。
            - 生成 → 版本 / 原内容 / 取消 / 重试 / 结果位置。
            - 长任务 → Job / 重连 / 幂等 / 日志。
            - 外部 API → Secret / 域名 / 限流 / 数据离开本地。

        [接受标准]
            - 只纳入 Golden Path 必需、安全必需和数据完整性必需。
            - 其他明确进入 Backlog。

        [不接受的答案]
            - 把行业所有高级功能都列为 must
            - 因为“以后可能用”就扩大首版

    [3.6 · 用户控制权]
        [覆盖意图]
            Agent-native 不等于 Agent 独占控制。用户需要知道发生了什么、能阻止什么、能恢复什么。

        [主问题]
            - 哪些 Agent 行为用户必须先确认？
            - Agent 工作时用户还能继续编辑吗，旧结果到达时怎么处理？

        [追问深化]
            - 用户说“全部自动” → “删除、覆盖、发布、外发数据也自动吗？按风险分级。”
            - 用户说“工作时锁住整个 UI” → “短任务可以，长任务会阻塞。是否只锁受影响对象？”

        [接受标准]
            - 确认、取消、冲突和恢复边界明确。

        [不接受的答案]
            - “Agent 自己看着办”

[Phase 4 · 数据、权限与宿主]

    [4.1 · 输入输出边界]
        [覆盖意图]
            格式、数量和规模决定前端、处理管线、存储和验收。

        [主问题]
            - 给出首版必须支持的输入 / 输出格式、典型数量、最大规模。
            - 哪些格式明确不支持？

        [追问深化]
            - “所有常见格式” → 要求真实样本和首版白名单。
            - “无限数量” → 要求典型值和压力上限。

        [接受标准]
            - must 格式和规模可测试，非目标明确。

        [不接受的答案]
            - “越多越好 / 看机器性能”

    [4.2 · 权威状态]
        [覆盖意图]
            React 内存和聊天上下文都不是可靠数据库。必须知道状态归属和重开行为。

        [主问题]
            - 关闭 Plugin、关闭会话或换机器后，哪些东西必须还在？
            - 状态跟随项目、用户还是只跟当前会话？

        [追问深化]
            - 用户说“自动保存” → “保存到当前项目还是用户全局？多个项目要不要隔离？”
            - 用户说“不需要保存” → “Agent 结果和用户编辑刷新后丢失是否可接受？”

        [接受标准]
            - 持久化范围、隔离范围、重开恢复与临时状态明确。

        [不接受的答案]
            - “浏览器自己保存”

    [4.3 · 文件范围]
        [覆盖意图]
            文件访问既影响能力也影响安全。Plugin 安装目录是临时资源，不是用户状态目录。

        [主问题]
            - Plugin 只读写当前项目，还是需要用户明确选择的外部目录？
            - 哪些文件只读，哪些允许创建、覆盖或删除？

        [追问深化]
            - 用户说“整个电脑都能选” → “首版是否可以改成用户显式选择文件，并把产物复制进项目？权限更可控。”
            - 用户说“覆盖原文件” → “是否先备份或创建新版本，哪些操作必须确认？”

        [接受标准]
            - 最小文件边界和破坏性操作规则明确。

        [不接受的答案]
            - 默认任意绝对路径读写

    [4.4 · 网络与 Secret]
        [覆盖意图]
            外部网络会引入认证、CSP、隐私、限流和失败模式。

        [主问题]
            - 首版必须访问哪些具体服务或域名，为什么本地能力不够？
            - 需要什么密钥，数据会发出去什么？

        [追问深化]
            - 用户说“以后接 API” → “首版不依赖就放 Backlog，避免无谓网络权限。”
            - 用户说“用用户自己的 key” → “在哪里配置、谁能读、日志是否会泄露？”

        [接受标准]
            - 域名、目的、数据、认证、离线 / 失败行为明确。

        [不接受的答案]
            - “需要联网”但无具体服务
            - 把 Secret 写进仓库或前端 bundle

    [4.5 · 长任务]
        [覆盖意图]
            生成、渲染、分析可能跨分钟，必须定义生命周期。

        [主问题]
            - 单次核心任务最长多久？用户关闭 UI 或会话时，任务继续还是取消？
            - 需要进度、取消、重试、重连和历史中的哪些？

        [追问深化]
            - 用户说“后台跑” → “谁持有进程，重启后怎样找回，结果写到哪？”
            - 用户说“关闭就停” → “已产生临时文件怎么清理，用户是否收到明确状态？”

        [接受标准]
            - 任务状态机与用户预期足够清晰，至少可恢复或可明确失败。

        [不接受的答案]
            - “等它跑完”

    [4.6 · 多宿主差异]
        [覆盖意图]
            同一业务核心可以共享，但 UI surface、消息桥和验证必须按 target 区分。

        [主问题]
            - required target 的最低可接受体验是什么？另一个宿主没有同样内联 UI 时，Browser / Preview fallback 是否可接受？
            - 哪个宿主的体验定义产品基准？

        [追问深化]
            - 用户要求完全一致 → “可以统一业务契约，但宿主 surface 可能不同。是统一能力更重要，还是统一像素 / 窗口形态更重要？”
            - 用户说“以后再说” → 把非 required target 设 optional / deferred，不留模糊承诺。

        [接受标准]
            - 每个 target 有 tier、体验底线和延期边界。

        [不接受的答案]
            - 一个 target 验证成功视为全部成功

    [4.7 · 破坏性操作]
        [覆盖意图]
            删除、覆盖、发布、上传和执行命令需要显式风险边界。

        [主问题]
            - Plugin 会不会删除、覆盖、发布、上传或执行可能改变项目的命令？
            - 哪些必须用户确认，怎样恢复？

        [追问深化]
            - 用户说“像普通编辑器一样” → “普通编辑器也有撤销和备份。具体哪些动作不可逆？”
            - 用户说“自动发布” → “发布到哪里、用什么凭证、是否预览、谁确认？”

        [接受标准]
            - 风险动作、确认点、备份 / 回滚和权限最小化明确。

        [不接受的答案]
            - “用户既然装了就默认同意一切”

[Phase 5 · 首版边界、失败与验收]

    [5.1 · Must]
        [覆盖意图]
            首版需要一个可闭环的最小集合，不是所有相关功能的缩略版。

        [主问题]
            - 如果只能保留 3-5 个用户可感知能力，缺哪个就不能完成核心任务？
            - 哪一个闭环证明这个 Plugin 有价值？

        [追问深化]
            - 用户列十几个 must → “逐个问：砍掉它，Golden Path 是否断？不断就不是 must。”
            - 用户只说一个宏大功能 → 拆成输入、操作、Agent、结果、保存的最低闭环。

        [接受标准]
            - must 数量收敛，且每项都对 Golden Path 必需。

        [不接受的答案]
            - “都必须 / 先全做”

    [5.2 · 非目标]
        [覆盖意图]
            明确不做能保护计划、Checker 和用户预期。

        [主问题]
            - 哪些看起来相关，但首版明确不做？至少说 3 条。
            - 哪些高级体验可以用简单 fallback？

        [追问深化]
            - 用户说“没有非目标” → 从多用户、云同步、公共商店、任意格式、移动端、协作、计费、全宿主一致等给候选，让用户确认。

        [接受标准]
            - 至少 3 条具体非目标，不写“其他功能”。

        [不接受的答案]
            - “暂时不确定”

    [5.3 · 关键失败与恢复]
        [覆盖意图]
            失败行为是产品行为。至少核心路径最可能失败的一处必须有恢复。

        [主问题]
            - 这条流程最容易在哪一步失败？用户看到什么，怎样继续，不丢什么？
            - 文件丢失、Agent 失败、权限拒绝、旧结果冲突中哪个最关键？

        [追问深化]
            - 用户说“提示错误” → “提示后用户能重试、换输入、恢复原状态还是只能退出？”
            - 用户说“不会失败” → 用真实依赖逐项指出失败可能。

        [接受标准]
            - 至少一个失败场景有触发、提示、数据保护和下一步。

        [不接受的答案]
            - “友好提示 / 稍后重试”

    [5.4 · 性能规模]
        [覆盖意图]
            没有规模边界，测试无法判断首版是否达标。

        [主问题]
            - 首版典型项目多大、对象多少、文件多大、核心交互可接受多快？
            - Agent 或渲染任务等待多久需要进度或取消？

        [追问深化]
            - 用户说“越快越好” → 给实际档位：即时操作 <100ms、普通保存 <1s、AI 任务按阶段反馈等，要求确认业务底线。

        [接受标准]
            - 至少核心直接操作、加载 / 保存和长任务有可测底线。

        [不接受的答案]
            - “不卡就行 / 看电脑性能”

    [5.5 · Acceptance]
        [覆盖意图]
            AC 是 Checker 的合同，必须可执行、可观察、有样本和证据。

        [主问题]
            - 用一个真实样本，从安装开始演练，哪几个事实出现才算成功？
            - 哪个宿主、哪份文件、哪个 UI 状态或日志能证明？

        [追问深化]
            - 用户说“能正常使用” → “拆成安装、打开、输入、UI → Agent、Agent → UI、重开恢复六个可证据步骤。”
            - 用户说“生成结果好” → “质量依据是什么？固定样本、人工 rubric、尺寸、内容或结构？”

        [接受标准]
            - 每个 must 至少一个 AC。
            - AC 包含 Given / When / Then、target 和 Evidence。

        [不接受的答案]
            - “用户满意 / 没有错误 / 效果高级”

    [5.6 · 参考与反例]
        [覆盖意图]
            复杂交互用参考和反例能减少设计歧义，但不应成为没有参考就无法继续的硬门槛。

        [主问题]
            - 哪个现有工具的一项具体交互最接近？你只想学哪一点？
            - 有什么绝对不想变成的样子？

        [追问深化]
            - 用户说“像 Figma” → “是无限画布、选择模型、快捷键、协作还是属性面板？只能选相关部分。”
            - 用户说“不要复杂” → “具体不要哪种复杂：多层菜单、过多参数、模式切换还是项目管理？”

        [接受标准]
            - 有参考时具体到交互点；无参考时通过 Golden Path 也能继续。

        [不接受的答案]
            - 整体复制一个成熟产品
            - “高级 / 简洁 / 科技感”

    [5.7 · Backlog]
        [覆盖意图]
            记录有价值但不进入首版的想法，防止它们在开发中偷偷回流。

        [主问题]
            - 哪些能力值得以后做，但首版不依赖？
            - 它们进入哪个版本或满足什么条件才启动？

        [追问深化]
            - 用户想把 Backlog 变 must → 要求说明 Golden Path 哪一步因此断裂，否则保持 deferred。

        [接受标准]
            - Backlog 与 Non-goal 区分：Backlog 可能做，Non-goal 本轮明确不做。

        [不接受的答案]
            - 在 Spec 正文混用“以后可能”导致计划误实现
