---
name: plugin-design-interview-bank
description: 设计阶段向用户采访体验取舍时选题用；只问用户可感知的决策，实现决策留给 Architect，宿主能力查官方资料。
---

[定位]
    这不是视觉偏好问卷，也不是架构面试。
    每次只选择会改变用户控制权、关键交互、结果呈现或宿主体验的问题。

[决定类型]
    - User Decision：用户必须选择的体验取舍，才使用本题库采访。
    - Architect Decision：直接设计并记录，不问用户。
    - Platform Fact：查官方文档和运行 Probe，不让用户猜。

[用户面前不暴露]
    不说 Wave、Gate、Class、Tool 分类、Threat ID 等内部词。
    用场景和结果提问。

[维度索引]
    1. 工作区与第一屏
    2. 核心对象与直接操作
    3. 选择、历史与恢复
    4. Agent 触发与上下文
    5. 结果应用与用户控制
    6. Agent 工作状态与并发
    7. 文件、资源与导出体验
    8. 多宿主体验与 fallback
    9. 视觉密度与可访问性
    10. 失败、冲突与边缘状态

[1 · 工作区与第一屏]

    [决定类型]
        User Decision + Architect Proposal

    [覆盖意图]
        第一屏决定用户如何进入任务、当前上下文是否清楚，以及主内容、操作和 Agent 状态谁占主导。

    [主问题]
        - 用户打开后，最应该占据视线的是正在编辑的内容、输入配置，还是 Agent 任务结果？
        - 是直接恢复上次项目，还是先显示“选择 / 创建 / 导入”的明确入口？

    [追问深化]
        - 用户说“都要” → “哪个必须一直可见，哪个可以折叠？屏幕空间要有主次。”
        - 用户说“像 IDE” → “具体要代码编辑、文件树、面板，还是只要高信息密度？不要复制整套 IDE。”
        - 用户说“打开就自动识别” → “多个候选或识别失败时，用户怎样确认当前项目？”

    [接受标准]
        - 主工作区、辅助区域、当前项目 / 对象 / 任务和空状态 CTA 明确。
        - 可以画出界面地图和首屏状态。

    [不接受的答案]
        - “简洁一点 / 参考 Figma / 都放上去”

[2 · 核心对象与直接操作]

    [决定类型]
        User Decision；对象数据结构由 Architect 决定。

    [覆盖意图]
        专业 Plugin 的价值常在直接操作。必须明确用户怎样找到、选中和改变核心对象。

    [主问题]
        - 用一个真实对象演练：用户怎样创建或导入它，怎样选中，最常改哪三个东西？
        - 用户动作完成时要立刻看到什么反馈？

    [追问深化]
        - 用户说“支持拖拽” → “拖的是素材、节点还是片段？放到空白、容器还是时间点？非法位置怎样反馈？”
        - 用户说“自由编辑” → “首版只保留哪三种核心编辑，不做完整专业软件？”
        - 用户说“自动布局” → “用户能否手动修正，自动布局什么时候触发？”

    [接受标准]
        - 核心对象、创建 / 导入、选择、3 个高频动作和反馈明确。
        - 明确哪些动作不触发 Agent。

    [不接受的答案]
        - “像正常编辑器一样”
        - 只有功能名，没有动作和状态变化

[3 · 选择、历史与恢复]

    [决定类型]
        User Decision：控制体验；Architect Decision：版本和存储实现。

    [覆盖意图]
        多选、撤销、历史和自动保存决定用户是否敢直接操作，也决定 Agent 怎样指代“这个”。

    [主问题]
        - 首版需要单选、多选、框选中的哪些？聊天里说“这个”时，当前选择怎样让用户确认？
        - 误操作最需要撤销哪一类？是一步撤销、版本历史，还是保留原结果并排比较？

    [追问深化]
        - 用户说“全部都要” → “核心任务是否真的依赖多选 / 框选？先定必须的选择语法。”
        - 用户说“自动保存就不需要撤销” → “自动保存会把错误也保存，恢复能力仍要定义。”
        - 用户说“永远保留所有版本” → “版本增长和资源清理怎样控制？首版保留最近 N 个还是显式版本？”

    [接受标准]
        - 选择模型、当前焦点、撤销 / 历史最低能力和保存时机明确。

    [不接受的答案]
        - “不容易误操作”
        - 把撤销和备份混为一谈

[4 · Agent 触发与上下文]

    [决定类型]
        User Decision：触发和可见性；Architect Decision：request schema。

    [覆盖意图]
        触发方式影响用户意图是否完整、对话与 UI 是否一致，以及 Agent 能否准确理解选择和范围。

    [主问题]
        - 用户更自然地在 UI 点“交给 Agent”，还是回聊天框发指令？两种都支持时，哪个是主路径？
        - 发送前，用户需要看到或编辑即将交给 Agent 的范围和说明吗？

    [追问深化]
        - 用户说“自动理解当前页面” → “当前页面可能有多个对象。是否在发送前高亮并显示选中项摘要？”
        - 用户说“边操作边自动调用 Agent” → “哪些操作表示意图完成？否则会重复触发和产生旧结果。”
        - 用户说“两种都一样” → “UI 按钮适合带结构化选择，聊天适合开放指令；是否统一落到同一 request？”

    [接受标准]
        - 主触发方式、辅助方式、发送前确认和用户可见上下文明确。

    [不接受的答案]
        - “AI 自己知道”
        - 每次 UI 状态变化都触发模型

[5 · 结果应用与用户控制]

    [决定类型]
        User Decision

    [覆盖意图]
        自动应用、预览确认、并排版本和提案模式影响信任、历史、速度和结果 Tool。

    [主问题]
        - Agent 的结果默认是直接生效、先预览确认，还是创建新版本并排放置？
        - 哪些结果可以自动应用，哪些属于覆盖、删除或发布，必须确认？

    [追问深化]
        - 用户说“越自动越好” → “可逆的小改可以自动，删除 / 覆盖 / 发布仍需确认，这个风险分级是否符合预期？”
        - 用户说“每次都确认” → “高频轻量操作会被打断。是否只对破坏性和高成本结果确认？”
        - 用户说“并排比较” → “选中一个版本后，原对象怎样处理？继续保留、归档还是替换当前指针？”

    [接受标准]
        - 默认结果策略和破坏性例外明确。
        - 原内容、确认和回退可走查。

    [不接受的答案]
        - “看 Agent 判断”

[6 · Agent 工作状态与并发]

    [决定类型]
        User Decision：体验；Architect Decision：Job / concurrency。

    [覆盖意图]
        Agent 工作可能持续数秒到数分钟。UI 是否锁定、用户能否继续改、旧结果怎样处理必须明确。

    [主问题]
        - Agent 工作时，用户可以继续操作其他对象吗？当前目标对象是锁定、可编辑还是显示“结果可能过期”？
        - 用户需要看到简单状态、阶段、日志还是可取消进度？

    [追问深化]
        - 用户说“全部锁住” → “长任务会阻塞整个工作区。是否只锁受影响对象？”
        - 用户说“完全不锁” → “用户修改后旧结果到达，是丢弃、提示冲突还是允许手动应用？”
        - 用户说“显示百分比” → “后端能否给真实进度？不行时用阶段而不是伪百分比。”

    [接受标准]
        - 可继续编辑边界、stale result 行为、状态层级、取消 / 重试体验明确。

    [不接受的答案]
        - “转圈等完成”用于长任务

[7 · 文件、资源与导出体验]

    [决定类型]
        User Decision：选择与产物体验；Architect Decision：路径和缓存。

    [覆盖意图]
        文件是用户可感知的一部分。导入、缺失、代理、下载和项目本地化需要明确体验。

    [主问题]
        - 用户导入文件后，是引用原位置，还是复制进当前项目？移动 / 删除原文件后怎样提示？
        - 最终产物默认保存到项目、系统下载目录，还是每次让用户选？

    [追问深化]
        - 用户说“直接用原文件” → “项目移到另一台机器会失效。首版是否提供复制进项目选项？”
        - 用户说“自动下载” → “文件名冲突、覆盖和多文件导出怎样处理？”
        - 用户说“视频直接预览” → “是否需要代理文件 / 缩略图，原始大文件不应进入模型上下文。”

    [接受标准]
        - 导入、资源缺失、保存、下载 / 导出和覆盖体验明确。

    [不接受的答案]
        - “浏览器默认处理”

[8 · 多宿主体验与 fallback]

    [决定类型]
        User Decision：可接受体验；Platform Fact：具体能力。

    [覆盖意图]
        required target 的产品承诺必须现实。不同宿主可共享能力，但 UI surface 和 Agent trigger 可能不同。

    [主问题]
        - 在 Claude Code required 版本里，如果不能像 ChatGPT / claude.ai 聊天端的嵌入 widget 一样内联，打开 Browser / Preview 工作区是否可接受？
        - 用户最不能接受的降级是什么：离开当前会话、手动复制上下文、没有全屏，还是不能实时回写？

    [追问深化]
        - 用户说“必须完全一样” → “可以保证业务和状态一致，但宿主窗口形态未必一样。哪一项一致性是真正必须？”
        - 用户说“只要能用” → “最低仍需定义：能打开、能传当前选择、能回写、能重开恢复。”

    [接受标准]
        - 每个 target 的用户体验底线和不可接受降级明确。
        - 具体技术路径留给 Platform Fact 验证。

    [不接受的答案]
        - “都可以”但无验收底线

[9 · 视觉密度与可访问性]

    [决定类型]
        User Decision：工作感觉与参考；Architect Decision：token 和可访问性规则。

    [覆盖意图]
        专业工作台和轻量向导需要不同密度。视觉必须服务核心内容和长时间使用，不是品牌装饰。

    [主问题]
        - 用户是偶尔完成一次任务，还是会长时间盯着这个界面工作？需要专业高密度还是轻量引导？
        - 哪个现有工具的一项具体视觉 / 交互感觉值得参考，哪一点绝对不要？

    [追问深化]
        - 用户说“高级科技感” → “转成具体：深色高密度、留白克制、状态低干扰、内容优先，哪两项是你要的？”
        - 用户说“像 Figma” → “参考它的画布占比、属性面板、快捷键还是视觉风格？”

    [接受标准]
        - 信息密度、主次、参考点、反例和长时间使用要求明确。
        - 键盘和焦点最低路径由 Architect补齐。

    [不接受的答案]
        - “简洁、现代、高级”

[10 · 失败、冲突与边缘状态]

    [决定类型]
        User Decision：恢复体验；Architect Decision：错误码与实现。

    [覆盖意图]
        空、Loading、失败、冲突、无权限和文件缺失必须有用户下一步，不只是红字。

    [主问题]
        - 核心任务失败时，用户最不能丢什么？他应该原地重试、换输入、恢复旧版本还是查看详情？
        - 用户修改与 Agent 结果冲突时，默认丢弃旧结果、创建候选版本，还是让用户比较？

    [追问深化]
        - 用户说“弹错误提示” → “提示之后用户做什么，当前状态和输入保留吗？”
        - 用户说“自动解决冲突” → “按什么规则，是否可能覆盖用户新修改？高风险时应变候选而不是静默合并。”

    [接受标准]
        - 至少空、Agent 失败、权限拒绝、文件缺失、版本冲突和重开恢复有明确行为。

    [不接受的答案]
        - “友好提示 / 自动处理”
