---
name: chatcut-captions
description: 当用户说「加字幕」「字幕这些」「把字幕做了」，或要校对、导出、烧录课程视频字幕时使用。旁白段直接用已知原文切分做到零错字，只有含真人原声的录屏才走语音识别并标记为可疑，合并后交用户校对，再烧录进画面并导出独立 SRT。不做翻译字幕与多语言。
---

[任务]
    给当前 ChatCut 工程生成一整套字幕：旁白段走已知原文、录屏原声段走识别，合并成一条时间轴，
    标清每条的来源交用户校对，最后烧进画面并导出独立 SRT。

[启动检查]
    - **先 `request_claim`**。用户在工作台点「生成字幕」时请求进的是 `.chatcut/requests/queue.json`，
        **不会**自动变成一次 Tool 调用；不认领就动手，界面上那次点击永远等不到回音，
        请求会一直挂在 pending / claimed 直到租约到期。
        认领拿到的 requestId **原样传给后续每一个 Tool**（`captions_generate` 的 requestId 参数），
        写回时队列条目才自动结单。做不成就 `request_resolve`（failed）或退回（released），不许让它烂在那儿。
        队列是空的它会明说，那就照常处理用户当前的对话请求。
    - 工程已打开（`.chatcut/` 存在）。没打开先用 chatcut-workspace 打开，别在这里替用户开。
    - 旁白已合成：字幕时长按每段配音的**实测时长**分配，没有配音就没有时间轴。缺就先去 chatcut-narration。
    - 依赖体检 `dependency_check`：
        - `filter:subtitles`（libass）与 `font:cjk` 属 core，缺任一直接停，不要烧一屏豆腐块出来。
        - `filter:whisper` 与 `whisper:model` 只影响识别路。缺它们时**旁白段的字幕照做**，
          只把含原声的录屏段标为待处理，并告诉用户模型多大、从哪来、放到哪。
    - 模型缺失不是静默降级的理由：把 `WHISPER_MODEL_MISSING` 里的下载地址、体积、目标路径原样转达。
    - **缺 `whisper:model` 时给出补齐这条路**，别只说不可用：`fetchActions` 里带着可照抄的调用。
        a. 先 `dependency_fetch({"id":"whisper-base"})` 出单子（不下载、不落盘），
           把「141 MiB、来自 huggingface.co、装到 ${CLAUDE_PLUGIN_DATA}/models、
           落盘后校验 SHA-256、不补只影响录屏原声识别」念给用户；
        b. 用户同意后 `dependency_fetch({"id":"whisper-base","confirm":true})` → jobId → `job_status`；
        c. 装完**再 `dependency_check` 复核** feature:asr 已消掉，再走识别路。
    - 但 `filter:whisper` 缺失时**不要**去调 dependency_fetch：那是本机 ffmpeg 的编译选项，
        补不了，只能让用户换一个带 whisper 滤镜的 ffmpeg 构建。分清这两者，别让用户白等一次下载。

[执行]
    1. 分路。逐段判定走哪条路，判据是"这段的声音是谁发的"：
        - TTS 合成的旁白段 → **已知文本路**。文本是用户自己写的，直接按标点与显示宽度切分，
          按字数比例分配时长。零错字，不经过任何识别。
        - 含真人原声的录屏段 → **识别路**。调 whisper 识别，每条打 `source: "asr"`。
        - 无人声的录屏段 → 不生成字幕。静音送进 whisper 会得到凭空编造的句子（已实测）。
    2. 起 Job：`captions_generate`，**带上启动检查里认领来的 requestId**，立即返回 jobId，
       用 `job_status` 轮进度，进度只报阶段名与已完成/总数，不编百分比。
       某个片段识别失败时任务照旧完成：已识别的字幕保留，缺哪几段写在 warnings 里，
       如实转达给用户，别把"少了两段"说成"已完成"。
    3. 合并。同一时间段上**已知文本永远压过识别结果**：旁白的原文没有理由被机器猜测覆盖。
    4. 交校对。把结果指给用户看界面上的字幕列表：识别来源带虚线边框、斜纹底与「识别」徽标，
       告诉用户只需要盯这些条，原文那些不用看。**不要替用户改识别结果的措辞**——
       专有名词该怎么写只有用户知道，你改了他还得再核一遍。
    5. 烧录与导出。用户校对完再烧：字幕烧进画面，同时导出同源的独立 SRT。
       字体走本机文件绝对路径，永远不依赖网络字体或系统默认字体。

[完成标准]
    - 每条字幕都有 `source`，且旁白段的字幕拼接后与旁白原文逐字相同。
    - 识别来源在界面上可见地区别于原文来源，形状与文字都区分，不只靠颜色。
    - 抽帧检查：中英混排字幕正常显示、无豆腐块、不越出安全区。
    - 独立 SRT 的条数与时间轴与烧录完全一致。
    - 任一条不满足就说清楚差在哪，不要报"已完成"。

[禁止]
    - 不 `request_claim` 就直接执行界面提交的字幕生成，或调 `captions_generate` 时丢掉 requestId。
    - 翻译字幕、生成多语言字幕、双语字幕——不在本插件范围内，用户要就直说不做。
    - 给 TTS 旁白段跑语音识别。文本已知却去识别，等于自找错字。
    - 润色或"顺一下"旁白段的字幕文本。那会直接破坏逐字一致。
    - 未经用户确认就烧录：烧进画面是不可逆的，必须先校对。
    - 用系统默认字体或网络字体烧录中文。
    - 替用户下载模型或安装依赖之前不说明体积与来源。
