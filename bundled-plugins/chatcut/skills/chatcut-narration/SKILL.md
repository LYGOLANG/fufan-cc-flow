---
name: chatcut-narration
description: 当用户要给课程视频配音、写或修改旁白、说改一句重新生成、或要按配音时长重排时间轴时使用。把旁白原文改写成 TTS 友好文本、逐段合成语音、以实测时长驱动时间轴重排。
---

[任务]
    把旁白文本变成配音，并以配音的实测时长重排整条时间轴。

[启动检查]
    1. **先 `request_claim`**。用户在工作台点「生成配音」时请求进的是队列，不会自动变成 Tool 调用；
        不认领就动手，界面上那次点击永远等不到回音。把拿到的 requestId 原样传给后续每一个 Tool
        （`narration_synthesize` 等），写回时队列条目才结得掉。
        队列是空的就照常处理用户当前的对话请求，不影响往下走。
    2. 确认 MiniMax 凭据已配置。缺失时**把配置方式原样念给用户**，见下节，然后停下等他配好，不要反复重试。
    3. 确认工程里有旁白段落。没有就先请用户写，或按用户要求先起草。

[MiniMax 凭据怎么配]
    只有两个值：`MINIMAX_API_KEY` 与 `MINIMAX_GROUP_ID`，在 MiniMax 开放平台控制台的
    账户/密钥页面同时拿到（本插件的 TTS 走**国内站** `https://api.minimax.chat`，
    请用国内站账户的密钥，国际站的 key 在这个域名上会被判 invalid key）。
    **两者必须属于同一个账户**，混用会让接口返回 `1004 token not match group`——
    那不是网络问题也不是余额问题，重试多少次都一样，只能重新配。

    两条路，环境变量优先于配置文件：

    1. 环境变量（临时覆盖、CI 用）
        Windows PowerShell：`$env:MINIMAX_API_KEY="..."; $env:MINIMAX_GROUP_ID="..."`
        要长期生效用 `setx`，设完**重启宿主**才读得到。

    2. 用户级配置文件（推荐，配一次就好）
        Windows：`%APPDATA%\chatcut\credentials.json`
            （展开后通常是 `C:\Users\<用户名>\AppData\Roaming\chatcut\credentials.json`）
        macOS / Linux：`~/.config/chatcut/credentials.json`
        目录不存在就自己建。文件内容就是两个字段：

        ```json
        {
          "apiKey": "填你的 API Key",
          "groupId": "填你的 GroupId"
        }
        ```

    几条边界，说错了用户会白折腾：
    - **绝不要把凭据写进项目目录或仓库**。项目会被提交、打包、分享，凭据不该跟着走。
    - 文件损坏（JSON 语法错、字段缺一个）与文件不存在走同一条路，都要求重新配置。
    - 配完让用户重新发起一次配音即可，不需要重开工作台。
    - **不要替用户去读、回显或转述这个文件里的值**，也不要让他把 Key 贴进对话——
      你只需要知道"配好了没有"，不需要知道值是什么。

[执行]
    1. 调用 `narration_rewrite` 做 TTS 友好改写，把改写结果连同命中的规则一起给用户看。
        改写只作用于送 TTS 的文本，屏幕上显示的文字永远是用户写的原文。
        用户对某一句不满意可以手工覆盖，覆盖后不再被规则改写。
    2. 调用 `narration_synthesize` 逐段合成，**带上启动检查里认领来的 requestId**。
        这是长任务，用 `job_status` 汇报阶段与计数。
    3. 合成完成后调用 `timeline_retime`，各片段与标注的时刻按配音实测时长重排。
    4. 向用户汇报：每段多长、整条旁白多长、时间轴有没有产生告警。

[失败处理]
    某一段失败不影响其他段，已成功的音频不会被清除。
    - 1004：凭据与 Group 不匹配，引导用户重新配置，重试没有意义
    - 1008：余额不足，充值后重试即可，只会重跑失败的那一段
    - 1002：限流，可以重试
    重试时只请求失败的段，不要整批重来。

[增量重做]
    用户只改了某一段时，只有那一段会重新合成——其余段按内容哈希命中缓存。
    不要为了"保险"而全量重跑，那会浪费用户的额度和时间。

[完成标准]
    - 每段都有实测时长（来自 ffprobe，不采信接口自报值）。
    - 整条旁白音轨已生成，时长等于各段之和加段间静音。
    - 时间轴已按新时长重排，无重叠、无负时长。
    - 存在失败段时，明确告诉用户是哪几段、什么原因、怎么恢复。

[禁止]
    - 不 `request_claim` 就直接执行界面提交的配音，或调 `narration_synthesize` 时丢掉 requestId。
    - 用接口返回的 audio_length 当作时间轴依据。
    - 某段失败就把整批已生成的音频删掉重来。
    - 把改写后的文本写回用户原文。
    - 在日志或回复里带出 API Key。
